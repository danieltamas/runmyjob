## Outcome

Fixed (P1/P2): run ingestion marked complete only after every job of an attempt is stored (`done:` markers) and all attempts of a run are ingested;
rate limits abort the poll (thrown, every request gated, pause persisted, checkpoint untouched) including runner discovery; a bad answer when refreshing an
unfinished run is an incomplete poll (404 skipped as deleted); overlapping polls of one repo are a no-op; runner lists paginated and all scopes must answer,
a missing org PAT for a configured org scope gives no observation; stale-registration vs all-busy are rival causes (`unknown` when both fit); dependency wait
from sibling timings; parent attempt linked only on a unique job-name match; names, labels and runner names cleaned at every persistence boundary; destination
kept current on existing rows; rerun refuses a superseded attempt, refreshes the repo first and refuses when rules are invalid or GitHub is limited;
the watch loop keeps a due time per repo; GitHub rows are excluded from rx reconciliation (destination connectivity never changes a GitHub job's state);
org PATs wired from the Keychain (no prompt) or the one-time handoff.

Declined, with reasons:
- A rerun of an old completed run done outside RMJ is not seen until that run is refreshed (the list API has no updated-since filter; the window is creation time,
  as the spec says). Reruns through `rmj rerun` refresh the repo first.
- A first-page 304 skips later pages: only status changes of older runs are hidden, and those are refreshed by id while unfinished.
- A runner-list failure gives no observation (retried every poll while queued) and does not hold the checkpoint; the run data itself was read completely.
- `gh api -i` exits non-zero on 4xx; the parsed status is what callers act on, and every non-200 is an error to them.
- Destination attribution for completed jobs imported by backfill: ephemeral runners are already deregistered, so there is nothing to attribute from.
- A transition committing before `setGitHub` fails: the next poll compares the stored info separately and writes it again.

Deferred: GitHub job log fetching (failed jobs at once, others on demand) belongs with the log views; location of a running job is updated only from
registrations visible at that moment.
