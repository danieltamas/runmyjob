## Disposition

Fixed: 1 (scope bound to the spool, old lines discarded on a scope change), 3 and 4 (sink credentials redacted from every line, archive included), 5-7 (Elasticsearch answers: unreadable retries, 409 delivered, 401/403 pause, 408/429/5xx retry), 8 (requests also bounded to 4 MiB), 9 (a batch that cannot be set aside is renamed .bad, never deleted), 10 (one sink's write failure no longer starves the others), 11 (no network pass after the end flush), 14 (flushes serialized).

Accepted, open: 2 (a running CLI keeps the sinks it started with; the next run sees the change), 12 and 13 (unterminated line growth and synchronous spool writes, bounded in practice by the 1 MiB line clip and local disk), 15-23 (retention of idle spools, 256 MB cap exempts the newest file, GitHub stream limited to the report view, hand edits that keep the revision, no drainer for runs with no accepting sink, Retry-After dates, send-test strictness, status throttle details, indicator window), 24 (Datadog has a fixed intake host; pinned by unit tests).

## Second round: security persona and adversarial QA (Codex, same day)

Security (verdict was FAIL on the first cut). Fixed: every queued line is checked against the sink's current scope right before sending (replaces the .scope marker, which had races and a collision); the app's streamer rebuilds on any config change; runner PATs are redacted from streamed lines; Elasticsearch bulk answers need one acknowledgment per entry; Datadog tag values cannot add tags; requests capped at 768 KiB of text; unterminated output is cut at 1 MiB. Then the open items were closed too: a running CLI re-reads the config on every flush and drain and drops a sink that was switched off, removed or edited (it stays on the old config only until the next batch); the CLI is trusted for the Keychain item only when it is a signed binary, unmodified since signing, owned by the user and not group or world writable; a spool folder that is a link or belongs to someone else is not used; ingestor answers are read up to 256 KiB; each line of a multi-line secret is redacted; quarantined batches count as rejected; line assembly searches only new bytes for a newline and classifies only the first 2048 characters of a line. Measured: a dead sink adds the 3 s end flush to a run (0.22 s to 3.32 s for `echo hi`); a 5 MiB single line adds about 2.4 s more in a release build (debug is slower). Not covered by a test: the CLI trust check and the symlink check (no acceptance test exists for them).

QA (CLI and spool; the sandbox denied localhost listeners, so delivery and HTTP retries were covered only by sinks-check.sh and the unit tests): a non-object entry in log_sinks crashed the CLI (fixed, entry skipped); a failed spool write was silent (now the sink's last error); quarantined batches were not counted (now counted as rejected); a 5 MiB line was slow (see above). 100k lines in order, 8 concurrent runs with no loss or duplicates, and the tenant purge on a scope change all passed.
